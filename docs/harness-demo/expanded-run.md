# 긴 프롬프트 입력과 40개 Task 확장

2026-09-04 사용자의 회색 CLI 입력 영역 확장·긴 문장 잘림 수정·Task 증가 실행 요청을 반영했다. 회의 최종 합의(18:42)의 40개 Task와 가로 스크롤, 12:45의 총 실행 20분 유지가 기준이다. 이전 [단계별 검증 기록](validation.md)의 10개 Task는 당시 버전의 기록이다.

## 긴 문장 입력

회색 입력 영역은 기본 3줄의 본문과 위아래 여백을 제공하며 내용에 맞춰 늘어난다. 터미널 폭에 맞게 한글·영문·이모지를 줄바꿈하고, 입력 앞부분을 잘라 버리는 기존 한 줄 표시를 제거했다.

- Enter: 입력 제출
- Alt+Enter: 줄바꿈
- 방향키: 커서 이동과 긴 입력의 앞뒤 확인
- Home / End: 입력 시작과 끝으로 이동
- Backspace / Delete: 커서 앞·뒤 글자 삭제

터미널 높이를 넘는 입력은 커서 주변 줄을 표시하며 전체 입력값은 보존한다. 줄 범위 표시와 ↑↓ 이동으로 다른 부분을 확인한다. 창 너비가 바뀌면 현재 입력을 새 너비에 맞춰 다시 표시한다. 붙여넣기와 한글·이모지 조합은 표시 단위로 처리한다.

## 40개 제품 Task

| 기능 묶음 | Task | 내용 |
| --- | --- | --- |
| Product Planning | 1~4 | 제품 목표, 사용자 여정, 구조, 완료 조건 |
| Design & App Shell | 5~8 | 토큰, 탐색, 컴포넌트, 반응형 화면 |
| Identity & Profile | 9~12 | 사용자 모델, 인증, 프로필, 접근 정책 |
| Preference Onboarding | 13~16 | 취향 분류, 식단 제한, 입력 화면, 저장 |
| Lunch Matching | 17~20 | 후보, 점수, 그룹 제약, 매칭 검증 |
| Restaurant Discovery | 21~24 | 식당 데이터, 위치, 필터, 추천 카드 |
| Group Coordination | 25~28 | 모임, 초대, 투표, 결정 동기화 |
| Notifications | 29~32 | 이벤트, 전달 큐, 리마인더, 사용자 설정 |
| Release Validation | 33~36 | 여정 데이터, 통합, 기기, 복구 검증 |
| Production Release | 37~40 | 패키징, 환경 설정, 배포, Health Check |

모든 Task는 고유 제목·목표·담당·의존성을 갖는다. 0/40부터 구성하고 전체 구성이 끝난 후 순차 실행한다. 각 기능 묶음은 두 열·두 행으로 배치하며 노드의 크기를 유지한 채 가로로 확장한다. 가로 스크롤·좌우 버튼·현재 Task 보기로 이동할 수 있고 실행 Task 변경 시 자동으로 해당 위치를 보여준다. CLI fallback의 목록도 스크롤할 수 있다.

| 시간 | 데모 모드 | 테스트 모드 7× |
| --- | ---: | ---: |
| Task 구성 전체 | 200초 | 약 28.6초 |
| Task 1개 구성 간격 | 5초 | 약 0.7초 |
| Task 1개 실행 | 30초 | 약 4.3초 |
| 40개 실행 전체 | 20분 | 약 2분 51초 |

Task 20과 36의 실패·복구·재시도 이벤트도 30초 안으로 조정했다. 기존 STEP 1~5 원문 다이어그램, 6번째 입력의 Loom 직접 진입, RESET, Presenter, 최종 URL/QR은 유지한다. 카운트·타이머·복원 상한은 실제 Task 데이터 길이를 사용하며 새 저장 상태 v3로 이전 10개 Task 실행과 구분한다.

## 검증

환경: macOS arm64, Node.js v25.9.0, npm 11.12.1, 로컬 개발 서버와 Codex 내장 브라우저.

- 실제 PTY에서 1,000자 한글·영문·결합 문자·이모지 및 4개 논리 줄의 정확한 제출을 확인했다. 붙여넣기 마커와 UTF-8 분할, CRLF, Home/End/방향키, 이모지 조합 삭제, Alt+Enter, 터미널 48→80열 변경을 통과했다.
- 16·40·80·160칸 폭의 긴 문장 줄바꿈에서 문자 손실과 폭 초과가 없음을 확인했다.
- 40개 고유 ID·제목·의존성, 41개 그래프 노드(제품 입력 포함), 10개 기능 묶음, 노드 겹침 없음, 모든 연결의 유효성을 확인했다.
- 각 이벤트가 0~30초 안에서 순서대로 진행하고 마지막 완료 이벤트가 30초이며, 40개 합계가 1,200초임을 검사했다.
- 브라우저에서 제출 직후 `00 / 40`, 보이는 Task 0개, 전체 구성 후 40개 노드를 확인했다.
- 발표 화면에서 그래프의 가로 영역 5,188px, 화면 내 영역 약 1,376px을 확인했고, 끝까지 스크롤해 40번 노드 전체가 보이는 것을 확인했다. 현재 Task 보기로 복귀했다.
- 24번 Task에서 일시정지 후 CLI fallback으로 전환했다. 40개 목록과 현재 Task 추적을 확인하고, 새로고침 뒤에도 24번·진행 시간·fallback·일시정지가 복원됨을 확인했다.
- 정상 타이머를 60×로 가속해 나머지를 실행했고, 40/40 완료와 결과 화면·기존 URL·QR SVG를 확인했다. 결과 강제 표시나 Task 건너뛰기로 완료시키지 않았다.
- 결과 화면에서 RESET 후 빈 제품 프롬프트, 완료 0/40, 테스트 모드 7×가 복원됐다. 다시 제출하면 00/40·보이는 Task 0개부터 시작했다. 검증 후 빈 제품 프롬프트로 정리했다.
- 브라우저 오류 로그는 없었다. 1440×900 뷰포트 요청 시 브라우저 90% 배율로 CSS 영역은 1600×1000이었으며 위 스크롤 측정은 이 환경에서 수행했다. 임시 뷰포트 설정은 검증 뒤 해제했다.
- `npm run lint`, `npm run validate:scenario`, `npm run build`, `tsc --noEmit`를 통과했다.
- `git diff --check`, `loom docs index`, `loom validate --strict`를 통과했다.

실제 20분 대기는 가속 실행으로 대체했다. 외부 OHAYO 서비스 접속·모바일 QR 스캔·원격 게시 및 다른 OS의 터미널 실행은 이번 검증에 포함하지 않는다. 실행 중인 CLI에는 이전 코드가 로드되어 있으므로 `./demo-start`를 다시 실행해야 새 입력 패널이 적용된다.
